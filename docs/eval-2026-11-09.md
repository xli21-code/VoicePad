# ASR 引擎横评 · 2026-11-09

37 条真实口述（36 句脚本，1 条重录），全部由 VoicePad 自带归档（`~/.voicepad/audio/`）。
Gold 来自 `docs/eval-script.md`；`scripts/eval_report.py` 负责对齐与打分。

指标口径：
- **CER**：字符级编辑距离 / gold 字符数，**忽略数字格式（十/10）与语气词（呃/嗯）**。语气词是 ASR 应该转写的内容，删掉它们算改写层的活，不算识别错误。
- **术语存活**：gold 里的英文词（含 `Qwen3-ASR`、`p50`、`tail latency`）在输出里原样出现的比例。这是中英混说场景的核心指标。
- 重录/串行造成的异常项（CER > 1.0）单独列出，不进汇总。

## 结果

| 引擎 | 整体 CER | 术语存活 | 段2 中英术语 | 段5 长句 | 段7 中英混说 | 速度 |
|---|---|---|---|---|---|---|
| SenseVoice int8（现状） | 16.5% | 31/52 = 60% | 30.1% / 11-20 | 11.8% / 1-5 | 12.0% / 18-24 | 进程内，约 0.5–1s |
| Whisper large-v3-turbo（`--language zh`） | 19.4% | 25/47 = 53% | 14.2% / 13-20 | 11.5% / 3-5 | **49.0%** / 8-19 | 中位 1.3s（含进程启动） |
| **Whisper turbo + 术语 prompt** | **12.2%** | **39/47 = 83%** | **9.8% / 16-20** | **10.6% / 5-5** | **1.7% / 16-16** | 中位 1.7s（含进程启动） |

术语 prompt 就是把这批词当作 initial prompt 喂给 Whisper：

```
VoicePad, Magpie, Qwen3-ASR, SenseVoice, sherpa-onnx, CER, benchmark,
drawdown, hedge, tail latency, p50, p90, config schema, prompt, token,
API endpoint, Deepgram
```

### prompt 变体（同一模型，同一批 37 条，对齐冻结后可比）

| initial prompt | CER | 术语存活 | 有标点 | 含繁体 |
|---|---|---|---|---|
| 无 | 20.4% | 48% | 5/37 | 1/37 |
| 仅术语表（16 个词） | 15.8% | **88%** | 10/37 | 3/37 |
| 术语表 + 长标点示例句 | 18.5% | 71% | 20/37 | 0/37 |
| **术语表 + 短标点提示**（`简体中文，标点完整。例如：你好，今天开会。`） | **13.5%** | **87%** | **25/37** | **0/37** |

结论：标点提示有用，但**示例句越长越伤准确率**（长示例把术语存活从 88% 拉到 71%、CER 从 15.8% 涨到 18.5%）。定型为「短提示 + 术语表」。

## 三个结论

1. **Whisper 单独用会“吞掉”英文整句。** 强制 `--language zh` 且没有 prompt 时，中英混说段（段7）CER 49%，纯英文半句被直接丢掉（例：`The drawdown is mainly from the April correction，但是我们四月底已经减仓了` → 只剩后半句）。加了术语 prompt 之后同一句完整还原，段7 CER 降到 1.7%。
2. **术语 prompt 是最高杠杆的单点改动，比换引擎便宜得多。** 段2 从 30.1% → 9.8%，段5 的英文术语从 1/5 → 5/5。这类“热词”能力 SenseVoice 没有对应接口，Whisper 有（`--prompt` / in-process `promptTokens`）。
3. **Apple SpeechTranscriber 这条路暂时走不通**：本机只有 Command Line Tools 15.5 SDK，`SpeechAnalyzer` / `SpeechTranscriber` 不在 SDK 里，装了也编不过（要 Xcode 26，约 10GB）。

## Whisper turbo + prompt 的残留问题

| 问题 | 证据 | 处理方向 |
|---|---|---|
| **完全没有标点** | 所有输出连成一片 | 交给改写层补标点（现在 prompt 里已有这条规则）；不要指望 ASR |
| **偶发繁体** | `換` / 整句 `這就先把…定下來` | 确定性繁→简归一，放在 `TextProcessor` 预处理 |
| **偶发翻译漂移** | 一条 8.5s 片段被输出成英文翻译 | 短片段 + prompt 的已知风险；改写层加“同语言输出”检查 |
| **段1 略退** | 15.1% vs SenseVoice 12.8% | 纯中文短句上 prompt 会带少量噪声（`不接了`→`不介了`） |
| **模型体积** | turbo ≈ 1.5GB CoreML | 可接受；仍需保留 SenseVoice 作为后备 |
| **依赖** | 需要 WhisperKit SPM（macOS 14+） | 无 SDK 26 限制，可用 |

## large-v3（全量）为什么没选

在 37 条上跑 `openai_whisper-large-v3` + 同一份 prompt，CoreML 默认算力：**345.9 秒处理约 330 秒音频（RTF ≈ 1.0）**，单句 8 秒级；换成 GPU 也只是把加载时间压下来，解码仍显著慢于 turbo。这个数字直接 disqualify，没有再纠结它的准确率（fold 模式的输出顺序与文件名不对应，我也没有拿到可信的逐条分数，不拿它当依据）。

对照：turbo + prompt 单句 1.3–2.2s（含进程启动），App 内约 0.6–1.2s。

## 工程落地（T12）

- **WhisperKit 的 macOS 默认算力是 ANE，在这台机器上会卡死在 CoreML 模型加载里**（进程 CPU 0%、6 分钟无进展、内存先涨到 2.2GB 再回落）。改成 `melCompute/audioEncoderCompute/textDecoderCompute = .cpuAndGPU` 后 **17 秒加载完成**，稳定在 RSS ≈ 2.0GB。这一条是踩出来的，不是文档里的默认值。
- 模型放在 `~/.voicepad/models/whisperkit/`（Hub 缓存布局），启动时本地命中就不再联网；缺失才下载（约 1.5GB）。
- 主备结构：`ASREngine` 协议 + `WhisperKitEngine`（主）+ `SherpaRecognizer`（SenseVoice，兜底）。Whisper 未就绪或解码失败/空输出时自动回落，用户不会因为模型在下载或解码失败而丢一次口述。
- `pairs.jsonl` 现在多记一个 `asr_engine` 字段，后续可以直接按引擎分组复盘。

### 算力放置实测（M4 Pro / macOS 26.6，进程内，同一批片段）

| encoder | decoder | 加载 | 每句解码（7.8–10.2s 音频） |
|---|---|---|---|
| ANE | GPU | **125s 后卡死** | — |
| GPU | GPU | 14–18s | 1.62s |
| GPU | **ANE** | 19s | **1.22–1.24s** |
| ANE | ANE（WhisperKit 默认） | 6 分钟未返回（CPU 0%） | — |

结论：**ANE 只能给 decoder，encoder 放 ANE 会死在 CoreML 的加载器里**；decoder 上 ANE 比 GPU 快 25%。另有一次性冷启动开销 3.3–3.8s，会正好落在用户第一次口述上——用 3 秒静音 + `noSpeechThreshold = 0` 在加载时先烧掉（否则静音会被判“无语音”3ms 返回，白等）。

## 还没测的

- **Qwen3-ASR 0.6B CoreML**（FluidAudio，beta）：中文预期强、原生支持 prompt/热词，但需要拉 1GB+ 模型和 SPM 依赖。
- **hotwords 直接进化器**（sherpa-onnx 的 transducer/paraformer 支持）：Whisper 的 prompt 是软条件，hotword 是硬约束，理论上更稳。
- **进程内延迟**：上面的 1.3–1.7s 含 ~0.8s 进程启动，接到 App 里应该更接近 0.6–1.0s。
